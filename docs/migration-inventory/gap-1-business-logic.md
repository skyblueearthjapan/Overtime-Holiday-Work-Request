### G1. サーバー側の「今日」「年度」「締め月」を JST で計算する決まりが計画書に無い（朝のピークが UTC では前日）

- 証拠（確認済み）: サーバーが「今日」を決めて結果を変える箇所が多い。
  - 通常の残業申請は送られた日付を捨て、サーバーの今日（JST）に置き換える（`formSubmit.gs:710-712`）。
  - 年度の始まり 3/16 と「未来日は不可」は**今日**を基準に判定する（`config.gs:108-117`・`131-139`・`162-178`）。
  - 承認者画面・TOP・二次承認の「今日」「期限超過」「30 日の窓」（`approval.gs:165`・`225-248`、`worklog.gs:410-420`・`449-457`）。
  - 締め月（15 日以前は前月分）・月の経過日数・年度の始まり（`staffSummaryApi.gs:13-43`、`adminApi.gs:146-156`・`11-23`・`329`）。
  - GAS はスクリプトの時間帯が `Asia/Tokyo`（`appsscript.json`。確認済み）なので、`new Date(y,m,d)`・`getDate()`・`setDate()` もすべて JST で動いている。
- 計画書: 4-2 は「日時は UTC の timestamptz」とだけ書き、4-3 は「『今日』はブラウザの時計で決まる箇所が多い」と書く。サーバー側の日付計算を JST で行う決まりは本文に無い（01 §6.1 の末尾に一文あるだけ）。
- なぜ大事か: 提出の 7 割が朝 6〜8 時（計画書 2-1）。この時間は UTC ではまだ前日。コンテナの既定（UTC）の `date.today()` や `datetime.now().date()` を使うと、朝の通常残業がすべて前日付で登録される。3/16 の朝 0〜9 時には年度の判定も 1 日ずれる。
- 直し方: 4-2 に「サーバー側の日付の計算（今日・年度 3/16 と 4/1・締め月 16〜15・月の経過日数・30 日窓・7 日窓）は、すべて `Asia/Tokyo` の日付で行う。`date.today()` は使わず `timeutil` の JST 関数だけを使う」と書く。受け入れ試験に「06:30 JST に通常残業を出すと targetDate が当日になる」「3/16 08:00 JST に 3/15 の遡及残業が拒まれる」「15 日 23:30 と 16 日 00:30 の締め月」を入れる。
- 確かさ: 確認済み（コード）。VPS で起きるかは実装しだいなので推測。

### G2. worker の並行実行で、蓄積台帳の行と PDF の日付フォルダが壊れる

- 証拠（確認済み）:
  - 台帳の upsert は「1 列目を読んで無ければ `lastRow + 1` に書く」（`mail.gs:676-700`）。同じ年度タブに 2 つが同時に書くと、同じ行を取り合って片方が消える。
  - GAS では、完了・編集・削除・総務の手動入力・Sebastian の PDF と台帳の処理は**全体ロックの中**で動く（`worklog.gs:144-212`・`253-341`・`541-646`・`653-699`、`adminApi.gs:435-517`、`api.gs:74-128`）。ロックの外で動くのは承認と二次承認のフェーズ 2 だけ（`approval.gs:328-341`・`454-473`・`745-760`・`846-865`）。そのため、今は取り合いがほとんど起きない。
  - 一括承認・一括二次承認（最大 50 件）は、台帳の upsert を立て続けに出す。
- 計画書: 4-6 は「申請 1 件の仕事は同時に 1 本、積んだ順」。別の申請の仕事どうしは同時に動いてよい書き方になっている。4-7 は台帳の並行について触れていない。
- なぜ大事か: VPS の worker が台帳の仕事を 2 本以上同時に動かすと、一括承認のたびに台帳の行が抜けたり上書きされたりする。総務が使う台帳の中身が変わる。PDF の日付フォルダ（`yyyy.MM.dd`）も「無ければ作る」の取り合いで二重にできうる（推測）。
- 直し方: 4-6・4-7 に「台帳の仕事は全体で 1 本ずつ（年度タブ単位の直列でもよい）。PDF の日付フォルダを作る処理も直列にする」と書く。受け入れ試験に「完了済み 20 件を一括承認し、台帳に 20 行が重ならずに入る」を足す。
- 確かさ: 取り合いの形はコードで確認済み。VPS で起きるかは worker の作りしだい（推測）。

### G3. 承認と完了が同時に起きると PDF が作られない（行ロックをどこに掛けるか）

- 証拠（確認済み）: 承認は「status を approved にしてから WorkLogs の `actualEndAt` を見て、完了済みなら PDF」（`approval.gs:314-321`）。完了は「WorkLogs を書いてから、status が approved なら PDF」（`worklog.gs:173-204`）。GAS は同じ全体ロックで両方を直列にしているので、どちらかが必ず PDF を作る。
- 計画書: 4-2 は「行ロックは申請 1 件ごとの `SELECT … FOR UPDATE`」。完了や開始が `work_logs` だけを触る作りだと、`requests` の行をロックしない。
- なぜ大事か: 両方が相手の書き込み前の状態を読むと、どちらも PDF を作らない。朝バッチは「前日が対象日の approved」しか拾わない（`mail.gs:1454-1465`、`pdfExport.gs:570-600`）。対象日が 2 日以上前なら PDF は永久に作られない。
- 直し方: 4-2 に「`work_logs` を変える処理（完了・開始・総務の手動入力・Sebastian の 3 action・削除）も、先に `requests` の同じ行を `FOR UPDATE` でロックする」と書く。一括処理は ID を並べ替えてからロックする（デッドロックを防ぐ）。

### G4. `PDF_MODE` は「direct を含むか」で判定している。値は `direct` ちょうどではない

- 証拠: 判定は `normalize_(getSettings_()['PDF_MODE']).indexOf('direct') >= 0`（`approval.gs:331`・`457`、`worklog.gs:197`・`326`・`618`、`adminApi.gs:500`、`pdfExport.gs:577`）。本番の Settings の値は「`direct で直接書込方式（未設定=XLOOKUP方式）`」という文（控えの Settings.csv で確認済み）。
- 計画書: 4-0 は「`PDF_MODE`=direct」と書いている。これを読んで「`== 'direct'`」と作ると、本番の値では偽になり、すべて XLOOKUP 方式で作ってしまう。
- 直し方: 4-0 の値を「`direct で直接書込方式（未設定=XLOOKUP方式）`（`direct` を含むので直接方式）」に直す。仕様書に「含むかどうかで判定する」と書き、試験を 1 本足す。

### G5. 丸めと分の切り捨てが JS と Python で違う

- 証拠（確認済み）:
  - 実働分は `Math.round(ミリ秒差 / 60000)`（`worklog.gs:169`・`298`、`api.gs:88`・`215`、`adminApi.gs:475`）。
  - 休憩の窓の判定は `yyyy-MM-dd HH:mm` に書式化してから分で比べる。秒は捨てる（`worklog.gs:113-127`）。19:30:40 に押すと 19:30 とみなし、19:20-19:30 の窓を「含む」。
  - 月次の予測は `Math.round(pace * daysInMonth)`（`adminApi.gs:203`）。滞留時間は `Math.floor`（`adminApi.gs:415`）。残業の予定は `Math.round(n * 60)`（`formSubmit.gs:407`）。
  - Python の `round()` は偶数への丸め（`round(14.5) == 14`）。JS の `Math.round(14.5)` は 15。月次の予測は割り算なので .5 がふつうに出る（例: 1 分を 2 日で割り 31 日を掛けると 15.5）。
- 計画書: 触れていない。5-4 の総当たり比較でまれに不一致が出ても、原因がわかりにくい。
- 直し方: 仕様書に「`Math.round` は `floor(x + 0.5)`、`Math.floor` は `floor`。休憩の窓は JST の時・分だけで比べる（秒は捨てる）。実働分は秒を含む差を丸める」と書く。境界の試験（19:29:59・19:30:00・19:30:40、予測が .5 になる例）を足す。

### G7. 二次承認は前の PDF を先に捨てる。作り直しに失敗すると、そのまま PDF が無くなる

- 証拠（確認済み）: 二次承認はロックの中で前の PDF をゴミ箱へ移し、3 列を空にする（`approval.gs:736-738`・`834-837`、`873-883`）。作り直しはロックの外で 1 回だけ試し、失敗はログだけ（`approval.gs:747-754`・`849-856`）。編集も同じ順（`worklog.gs:611-626`）。朝バッチは対象日が前日のものしか拾わない（G3 の証拠）。完了や承認のときの PDF 失敗も警告だけ（`worklog.gs:201-203`、`approval.gs:338-340`）。
- 計画書: 6-5 は「完了済みで PDF なしの 25 件は触らず、原因を調べる（Q13）」。4-6 は「前の PDF はゴミ箱へ（今と同じ）」。失敗したときの扱いは書いていない。
- なぜ大事か: 25 件の原因の候補になる（推測。二次承認・編集の作り直しの失敗、完了時の失敗で、対象日が前日でなかったもの）。VPS の outbox は再試行するので、同じ失敗でも PDF ができる。月次の「PDF 未作成」の数が GAS と変わる。
- 直し方: 6-5 の調べ方に「25 件の `approvedAt2`・`modifiedAt` と、完了日と対象日の差を見る」を足す。4-6 に「再試行で PDF ができるのは意図した差」と書き、変える／変えない一覧に載せる。前の PDF を捨てる時点（新しい PDF ができてから捨てるか）を仕様で決める。

### G8. 蓄積台帳に書く・消すきっかけの一覧が計画書に無い

- 証拠（確認済み）:
  - upsert するのは、完了（画面 2・Sebastian 2・総務の手動入力）、承認したときに完了済みだった場合、二次承認、編集で PDF があった場合（`worklog.gs:207`・`336`・`630`、`api.gs:113`・`239`、`adminApi.gs:512`、`approval.gs:337`・`465`・`760`・`861-865`）。

  - 休日の日付を年度をまたいで直すと、古い年度タブに行が残る（01 Q7）。
- 計画書: 4-7 は「今の動きを同じ結果で再現」とだけ書いている。

### G9. 「承認の後で作業を完了した」場合と、その逆の場合の PDF の方式

- 証拠（確認済み）: どの方式で作るかは、PDF を作るきっかけによって決まる。
  - 一次承認・完了（画面）・編集・総務の手動入力は `PDF_MODE` に従う。
  - 二次承認は、いつも直接方式（`approval.gs:750`・`851`）。
  - Sebastian の完了は、いつも XLOOKUP 方式（`api.gs:105`・`232`）。WorkLogs を `flush` せず、値を渡さずに呼ぶ。XLOOKUP 方式はシートの値を読むので、書いたばかりの実績が PDF に載るかはシートの反映しだい（推測）。
- 計画書: 3-1 と 4-5（Q3）でおおむね書けている。足りないのは「完了は承認済みのときだけ PDF を作り、すでに PDF があれば作り直さない（`already`）」と「二次承認の前に完了していれば作り直す」の組み合わせの表。
- 直し方: 4-6 の「作る場面」を、きっかけ×方式×既存 PDF の扱いの表にする（`already` で何もしない場面を含める）。
