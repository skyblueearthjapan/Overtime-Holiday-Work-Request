## 1. 計画の前提を変えた指摘（ディレクター判断 2026-11-26）

高の指摘の多くは「シートを毎晩の控えにすると、シートを直接読む仕組みが当日の申請を見られない」に行き着いた。

| 指摘 | 中身 |
|---|---|
| gap-5 高-1 | Sebastian は requestId を受け取るだけ。シートを読んで番号を得ている見込み（推測） |
| gap-5 中-8 | 統合メール通知システムは夕方 2 回・朝のメールを引き継いだ。DB を読む見込み（推測） |
| gap-5 高-3 | 業務NOマスタの転記は日報アプリのために残した（`3d6214b`） |
| gap-3 高-4・中-5 | PDF テンプレに Requests を引く数式。タブを作り直すと壊れる |
| gap-4 F-1・F-2・F-3、gap-5 高-2・中-9 | 書き出しで日時の型・表示形式・行の並びが変わると、戻した GAS が誤動作する |
| gap-3 高-1・高-2・高-3、gap-1 G2・G3、gap-3 中-1〜3 | PDF と台帳の順序・条件・直列性。別の GAS に切り出す案では `getActive()` が使えない |

**決定 A（シートへの反映）**: 毎晩のタブ置き換えをやめ、VPS の書き込みのたびに該当の行だけをシートへ反映する（行単位の upsert、数秒〜1 分以内）。行の位置と並び・日付の型と表示形式を保ち、行もタブも消さない。夜に全行の照合を行い、差があれば直して記録する。→ Sebastian・統合メール・日報アプリ・テンプレの数式・ロールバックが今と同じ形で動く。決定 #7・#8 の「書き出し」はこれで満たす（より細かい）。

**決定 B（PDF と台帳）**: PDF と蓄積台帳は、今の GAS（同じプロジェクト、DB に紐づいたまま）のコードをそのまま使う。VPS の worker が、行をシートに反映した後で GAS の内部用の入口（`doPost` の新しい action、token 認証）を 1 件ずつ呼ぶ。GAS 側は今の関数（`generatePdfDirect_`・`upsertAccumulationRow_` など）を今と同じ順序・条件で動かし、結果（pdfFileId など）を返す。VPS は結果を DB に入れる。→ PDF の見た目・台帳の中身・順序・失敗時の動きが今と同じ。利用者の画面は待たない。PDF の仕事は全体で同時に 1 本（直列）。

**決定 C（時刻）**: サーバーの「今日」・年度・締め月・日時の解釈は、すべて Asia/Tokyo で行う。06:30 JST の受け入れ試験を入れる（gap-1 G1）。DB スプレッドシートのタイムゾーン設定は段階 2 で読んで記録する（gap-5 高-2）。

**決定 D（マスタ同期）**: `syncAllMasters` は VPS の worker が今と同じ規則で行い、DB の同じタブ（業務NOマスタなど）にも今と同じ形で書く（日報アプリのため。gap-5 高-3、gap-4 F-6）。

決定 A・B の確かめ（スパイク）は段階 2 で行う。本番の DB のコピー（サンドボックス）で、行の反映 → GAS の PDF の入口 → 見た目の比較（10 件）→ 台帳への書き込みを通す。
