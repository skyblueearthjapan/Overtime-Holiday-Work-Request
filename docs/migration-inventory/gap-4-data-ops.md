## 高

### F-1 書き出しの日時セルが、新しい行では数値として読まれる（高）

- 根拠（確認済み・コード）: GAS は Requests の日時を「Date なら書式化、そうでなければ文字のまま」で読む。`approval.gs:193-198`・`approval.gs:627-640`。滞留の計算は `new Date(row[idx['submittedAt']])`（`adminApi.gs:397-398`）で、数値が来るとミリ秒とみなして 1970 年になる。PDF の手動作り直しも `submittedAt instanceof Date ? … : new Date(submittedAt)`（`pdfExport.gs:1008`）。
- 根拠（確認済み・控え）: `submittedAt`・`approvedAt`・`approvedAt2`・`pdfGeneratedAt`、BatchLogs の `実行日時` は日時のセル（gviz で `m/d/yyyy` 形式に出る）。
- 計画の記述: 5-5「シリアル値を RAW で書き、列の表示形式を保つ」を第一案とする。
- なぜ重要か: 既存の行のセルには表示形式が残る。ただし切り替え後に足す行（今の最終行より下）は表示形式が無いことがある（推測）。その場合、RAW の数値はただの数値になる。戻したとき、その行だけ一覧に `46352.29` のような数字が出て、未承認滞留（48h）の判定が全部「超過」になる。統合メール通知システムが同じ列を読んでいれば、そちらも狂う（推測）。罠 54 の「害は無い」は、時刻つきの文字を書いた前例の話で、この案には当てはまらない。
- 直し方:
  - 書き出しの値に加えて、書いた範囲の日時の列へ `repeatCell` で `numberFormat`（今の列と同じ型・パターン）を毎回当てる。
  - リハーサルで「書き出しで新しく足した行」を GAS（サンドボックス）の `getValues()` で読み、上の 5 列が `Date` で返ることを受け入れ条件にする（5-6 に追記）。
  - DB の地域設定も控える。gviz が `m/d/yyyy` で出るので en_US の見込みがある（推測。5-1 の【要確認】に足す）。

## 中

### F-2 書き出しで行・タブを消さない約束が書かれていない（中）

- 根拠（確認済み）: PDF の XLOOKUP 方式は、DB 自身のコピーの `操作!B3` に requestId を入れ、同じファイルの Requests を数式で引く（`pdfExport.gs:182-199`）。テンプレは DB 自身（計画 4-0）。マスタ同期は、書けないとタブを消して作り直す（`syncMasters.gs:73-79`）。
- 計画の記述: 5-5「データを先に書き、余りの行を後から消す」。消し方（値を消すのか、行を消すのか）は書かれていない。
- なぜ重要か: 行やタブを消すと、`申請書フォーム`・`操作`・`休憩計算_フォーム` の数式の参照がずれたり `#REF!` になったりする（推測。数式の中身は未確認）。ほかのファイルが `IMPORTRANGE` で読んでいる場合も同じ（推測）。
- 直し方: 5-5 に「余りは値だけ消す（`values:batchClear`）。行・列・タブの挿入、削除、作り直しはしない。`syncAllMasters` の作り直しの型は写さない」と書く。4-6 のスパイクの手順 1（全セルの数式の一覧）で、Requests を指す参照の形を確かめる。

### F-3 行の並びを保存しないと、戻した後の動きが変わる（中）

- 根拠（確認済み）: GAS は新しい行を末尾に足す（`formSubmit.gs:671`・`836`、`pdfExport.gs:618`）。「最新の承認済み」を下の行から探す関数がある（`pdfExport.gs:664`・`767`）。
- 計画の記述: 5-5 は「並びが変わりうるタブは行の集合として比べる」だけ。
- なぜ重要か: 書き出しの並びが申請 ID 順などに変わると、戻した後の「最新」の意味が変わる。人がシートを見たときの並びも変わる。
- 直し方: 移行で `sheet_row`（元の行番号）を各表に持たせる。書き出しは「元の行番号順、その後に VPS で足した行を作った順」で書く。照合は「集合が同じ」に加えて「移行した行は同じ並び」を見る。

### F-6 マスタのタブが古くなることと、移転モードの止め方がぶつかる（中）

### F-7 `getDb_()` を通らない入口がある（中）

- 根拠（確認済み）:
  - メニューの「全トリガー初期セットアップ」`setupAllTriggers_`（`menu.gs:17`・`200-209`）は `ScriptApp` だけを使う。`getDb_()` を通らずに 4 本のトリガー（1 分ごとの取り込みを含む）を作る。トリガーは押した人の持ち物になる。

  - `api_getHolidayCandidateDates` は `requireSheet_` の失敗を握りつぶし、従来方式で候補日を返す（`formMap.gs:293-296`）。従来方式は `CalendarApp.subscribeToCalendar` を呼ぶ（`formMap.gs:359`）。開いたままの古い画面からは、止まらずに動く。
  - `cleanupFormSubmitTriggers_`・`debugPollStatus_`（前半）も `getDb_()` の前に動く。
- 計画の記述: 6-3「画面から呼ぶ 30 関数と公開の保守関数は `getDb_()` の先頭で止める」「メニューは出るが押しても `getDb_()` で止まる」。

  - `restoreTriggersAfterRollback` は、作る前に同じ関数のトリガーが無いことを確かめる。
  - DB のスプレッドシートの編集者の一覧を控える（【要確認】）。`操作` タブにスクリプトを割り当てたボタンがあるかも見る（`spreadsheet-structure.md:28-30` に「ボタン配置等」とある。推測）。

### F-9 カレンダーの候補日は、曜日の列の文字をそのまま出す（中）

- 根拠（確認済み）: `api_getHolidayCandidateDates` は社内カレンダーの A〜D 列を位置で読み（`formMap.gs:246`）、ラベルを `M/d` と「C 列の曜日の文字」で作る（`formMap.gs:270`）。控えの曜日は `Sat`・`Sun`・`Mon` などの英語の略号（130 行すべて）。マスタに候補が無いときは Google カレンダー、それも無いときは計算した祝日に切り替わる（`formMap.gs:299-301`・`332-333`）。`appsscript.json` には calendar のスコープが無い。
- 計画の記述: 触れていない（4-8 はマスタの取り込みだけ）。
- なぜ重要か: VPS が曜日を日本語で計算すると、休日の候補の表示が `4/4(土)` に変わる。今は `4/4(Sat)` と出ている見込み（推測。画面では未確認）。年度の境目でマスタ元のカレンダーが延びていないと、計算した祝日に切り替わる。この経路を移さないと候補が空になる。
- 直し方: 仕様の「変えない一覧」に、曜日は C 列の文字そのまま、A〜D の位置読み、`出勤土曜` を除く、範囲は今週月曜〜来週金曜かつ今日以降、を載せる。切り替えの順も載せる。Google カレンダーの段は、スコープが無く失敗している見込み（推測）。計算した祝日の段（`getKnownJapaneseHolidays_`）を移す。今の画面で表示を 1 回見る。

### F-10 B-15 の「控えから写し戻す」道具が無い（中）

- 根拠: 計画の B-7 は Drive の複製で控えを作る。B-15 の戻しは「控えから写し戻して C へ」とだけある。

### F-11 `normalize_` を、見出し以外にも当てる必要がある（中）

- 根拠（確認済み）: `normalize_` は前後の空白を取り、全角の英数字を半角にする（`config.gs:99-103`）。マスタの値（部署・作業員コード・氏名・工番・在籍フラグ）、DeptApprovers の部署とメール、StampMap のメール、FormMap の値にも使っている（`masters.gs:28-36`、`deptAuth.gs:20-21`、`pdfExport.gs:119`）。業務NOマスタの見出しは全角の `業務ＩＤ`。StampMap に大文字を含むメールが 1 行あり、比べるときに小文字にしている。
- 計画の記述: 5-1 で「見出しの照合」にだけ書いている。
- なぜ重要か: 全角の部署名や工番がマスタ元に入ると、GAS では同じ部署になるが、VPS では別の部署になる。
- 直し方: 仕様に「マスタ・DeptApprovers・StampMap・Settings の値を比べる前に `normalize_` と同じ変換をする（Settings はキーの前後の空白だけ）」と書き、同じ値の組で GAS と VPS の結果を比べる試験を作る。

## 低

### F-12 マスタ同期の細かい動き（低）

確認済み（`syncMasters.gs`）。計画 3-1・4-8 は大筋で正しい。足すこと:

- 80 人の上限は、1 列目が空の行を捨てた後の「見出し＋先頭 80 行」（`syncMasters.gs:59-64`）。元の並び順で切る。
- 元のタブが見出しだけのとき、GAS は DB のタブを見出しだけに置き換える（`data.length` が 1 で「空」の判定を通る）。書けないときはタブを消して作り直す。VPS の「空・0 行なら上書きしない」は改善なので、仕様の「直すもの」に載せる。
- タブごとに失敗を握り、ほかのタブは続ける（`83-85`）。VPS も 1 タブの失敗で全部を止めない。
- Date は「JST の 0 時ちょうど → `yyyy-MM-dd`、それ以外 → `yyyy-MM-dd HH:mm:ss`」（`204-214`）。VPS が UNFORMATTED（シリアル値）で読むなら、マスタ元のファイルのタイムゾーンで日時に直してから同じ規則で文字にする。控えのカレンダーは 130 行とも `yyyy-MM-dd` なので、マスタ元は東京の見込み（推測）。
- GAS は文字を `setValues` で書くので、シートが数字や日付に読み替える。工番マスタの `取込日時` は日時のセルと文字が混ざっている（控え）。VPS がマスタ元を直接読むと、この読み替えが起きない。新旧の照合試験（4-8）は「マスタ元」ではなく「DB のタブを GAS の読み方で読んだ結果」と比べる。今の作業員コードは 4 桁の数字だけで、先頭が 0 のものは無い（控え）。
- 同期は、スクリプト全体のロックを最大 30 秒待って持つ（`29-30`）。VPS では要らない。
- 作業員マスタの今の列は `作業員コード・氏名・部署・担当業務・拠点・スタッフ種類` で、`Googleアカウント…` と `在籍フラグ` の列は無い（控え）。そのため `api_getWorkerInfo` はいつも `null`、`lookupWorkerEmail_` はいつも空を返す（`masters.gs:152-156`・`187-189`）。列が足されたら効く作りは残す。在籍フラグは「空なら在籍」の扱い（`masters.gs:34-37`）。
